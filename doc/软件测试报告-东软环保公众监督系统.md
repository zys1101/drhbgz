## 1 引言

### 1.1 编写目的

本文档主要阐述东软环保公众监督系统（NEUSOFT Environmental Public Supervision，简称 NEP）测试过程中的一些细节，为系统的测试工作提供框架和规范。确定项目测试的策略、范围和方法，主要有以下几点：

1. 确定项目测试的策略、范围和方法；
2. 使项目测试工作的所有参与人员（客户方参与人员、测试管理者、测试人员）对本项目测试的目标、范围、策略、方法、组织、资源等有一个清晰的认识；
3. 使项目测试工作的所有参与人员理解测试控制过程；
4. 从策略角度说明本项目测试的组织和管理，指导测试进展，并作为项目测试工作实施的依据；
5. 本文档是本项目测试整个过程进行的依据、规范和标准。

本项目测试涉及的两类人员及其主要职责如下：

- **测试管理人员**（项目经理、客户指派人员）：根据该测试计划制定进一步的计划、安排（工作任务分配、时间进度安排）和控制测试过程；客户指派人员通过该测试计划了解测试过程和相关信息。
- **测试人员**：根据该测试计划中制定的范围、方法确定测试需求、设计测试用例、执行和记录测试过程，并记录和报告缺陷。

### 1.2 项目背景

#### 1.2.1 系统描述

**系统名称**：东软环保公众监督系统（NEP）

**系统定位**：面向"公众监督—专业检测—决策分析"业务闭环的 Web 管理系统。汇总公众监督员提交的空气质量反馈，由系统管理员指派网格员（按 34 省 / 106 个大城市的网格化管理体系）实地检测，实测 AQI 数据经管理员确认后入库，最终面向决策者提供五项统计与可视化大屏。

**系统使用场景**（按角色划分四类用户）：

**（1）公众监督员（数据源头）**

1. 通过手机号注册成为公众监督员，并绑定所在网格地址（省-市-具体地址）；
2. 登录后可提交空气质量监督反馈（预估 AQI 等级 + 观测时间 + 文字描述）；
3. 可随时在"历史反馈"中查看本人反馈的处理状态与实测结果。

**（2）AQI 检测网格员（现场检测）**

1. 使用 HR 系统同步生成的登录编码（如 grid001）登录；
2. 在"我的任务"中查看管理员指派给自己的待检测反馈任务；
3. 到达网格区域实地检测后录入 SO₂、CO、PM2.5 三项污染物的浓度等级，系统按 AQI = MAX(SO₂AQI, COAQI, PM2.5AQI) 自动计算综合等级并上报；
4. 可提交请假申请，经管理员审批同意后进入请假（非工作）状态。

**（3）系统管理员（流程与数据管理）**

1. 登录后可在首页看板查看全局数据概况；
2. 在"监督数据列表"中按地区/地址/手机号/等级/状态/日期检索公众反馈，并向网格员指派检测任务（本地优先、异地就近），也可删除反馈；
3. 在"确认AQI数据"中审核网格员提交的实测数据，确认后纳入统计，异常数据可退回重新检测；
4. 查看五项统计报表（省级 AQI 统计、AQI 月度趋势、等级分布、实时优良率、网格覆盖率）与可视化大屏；
5. 在人员管理模块维护网格员账号（新增/编辑/工作状态）、审批网格员请假（同意/驳回/销假）、维护公众监督员档案。

**（4）决策者（可视化大屏）**

1. 使用专属账号登录后进入全屏可视化大屏，实时查看区域空气质量统计与分布。

#### 1.2.2 系统功能需求分析

本系统按"角色—模块"共实现 4 类角色、12 个功能模块：

**公众监督员端（NEPS）**

1. 登录注册模块（手机号注册、密码校验、用户类型切换）
2. 网格地址绑定模块（省-市-地址三级绑定）
3. 反馈提交模块（预估等级、观测时间、描述）
4. 历史反馈模块（本人记录、状态流转、实测结果回显）

**AQI 检测网格员端（NEPG）**

5. 任务列表模块（我的任务、任务统计）
6. 实测录入模块（三项污染物等级、AQI 自动计算）
7. 请假申请模块（事由、期间、审批状态跟踪）

**系统管理端（NEPM）**

8. 监督数据管理模块（查询/详情/指派/删除）
9. 确认 AQI 数据模块（确认/退回）
10. 统计报表与可视化大屏模块（五项统计、ECharts 大屏）
11. 人员管理模块（网格员 CRUD、请假审批、监督员档案）
12. AQI 级别管理模块（六级标准维护）

技术架构：前端 Vue3 + Vue CLI + Axios + Element Plus + ECharts（端口 8080，`/api` 代理至后端）；后端 SpringBoot 3.2.8 + MyBatis-Plus + springdoc-openapi（端口 9000，上下文 `/api`）；数据库 MySQL（`nep_system` 库，7 张表 + 34 省 / 106 大城市 / 6 级 AQI 标准种子数据）。

## 3 系统功能测试

### 3.1 系统功能及测试点

东软环保公众监督系统基于 Java（SpringBoot）+ MySQL + Vue3 开发，围绕"公众反馈 → 管理员指派 → 网格员实测 → 数据确认 → 统计大屏"的业务主线，实现了四类角色的完整闭环。核心数据状态机如下：

```
反馈状态：  待指派(0) ──指派──> 已指派(1) ──录入实测──> 检测中(2) ──确认──> 已确认(3)
                          退回 <──────────────────────────┘（退回后反馈重新回到 待指派(0)，可再次指派）
实测数据状态：待确认(0) ──确认──> 已确认(1)（纳入统计）
                       ──退回──> 已退回(2)（不纳入统计）
```

**表3-1 功能及各测试点表**

| 功能类别 | 功能名称 | 测试点描述 |
| --- | --- | --- |
| 认证管理 | 登录 | 四类角色（监督员/网格员/管理员/决策者）切换登录；正确账号密码跳转角色首页；错误密码、不存在账号、用户类型不匹配、非工作账号、空输入、未登录拦截等异常分支 |
| 认证管理 | 公众监督员注册 | 手机号格式（11 位、1 开头）、密码长度（≥6）、姓名、年龄（1~120）、性别校验；重复手机号拦截；注册后登录闭环 |
| 公众监督反馈 | 网格地址绑定 | 省-市级联选择、地址保存与回显；未绑定地址时禁止提交反馈并引导绑定 |
| 公众监督反馈 | 提交反馈 | 预估等级（6 级）、观测时间、描述（必填、500 字限长）；提交成功入库且状态为"待指派"；历史反馈仅显示本人记录并回显处理状态/实测结果 |
| 监督数据管理 | 反馈查询 | 关键字（地区/地址/手机号/描述）、预估等级、状态、日期范围组合过滤与重置 |
| 监督数据管理 | 指派网格员 | 待指派/检测中任务可指派；本地网格员置顶并标记"本地"；无本地人员时异地指派提示；非工作状态网格员不可选；指派后状态流转、进入网格员任务列表 |
| 监督数据管理 | 删除反馈 | 二次确认弹窗；删除成功且数据不可恢复 |
| 任务处理 | 我的任务 | 仅显示指派给自己的任务（已指派/检测中）；任务统计（待检测数、较高污染反馈数） |
| 任务处理 | 实测录入 | 三项污染物等级必录完整；AQI = MAX 三项自动计算并展示；提交后生成"待确认"实测数据、反馈状态转"检测中" |
| 任务处理 | 请假申请 | 事由、起止日期必填；提交后进入管理员审批队列；本人可查询审批状态 |
| 确认AQI数据 | 数据确认 | 待确认数据确认 → 纳入统计，反馈状态转"已确认"；支持按关键字/等级/状态查询 |
| 确认AQI数据 | 数据退回 | 退回后实测数据标记"已退回"，反馈回到"待指派"，可重新指派检测（闭环） |
| 人员管理 | 网格员管理 | 新增（登录编码唯一性）、编辑（姓名/地区/工作状态）、列表展示工作状态标签 |
| 人员管理 | 请假审批 | 同意（账号转非工作、禁止登录与接单）、驳回、销假（恢复工作）；重复审批拦截 |
| 人员管理 | 公众监督员管理 | 监督员档案列表、关键字检索、负责地区维护 |
| 统计报表 | 五项统计 | 省级 AQI 统计、AQI 月度趋势（12 个月）、等级分布、实时优良率、网格覆盖率；仅统计已确认数据；年度过滤 |
| 可视化大屏 | 决策大屏 | 决策者角色全屏大屏：区域统计图表、分布地图、趋势图渲染正确 |
| AQI级别管理 | 级别维护 | 六级标准（0~50 优 … 300 以上严重污染）列表、详情、新增/修改/删除 |
| 行政区划 | 省市数据 | 34 省列表、按省查询城市（106 大城市），供绑定/指派/统计使用 |

### 3.2 测试用例设计

#### 3.2.1 测试用例注意问题

- **对被测版本足够了解**：由粗到细解读需求文档与系统实现，重点关注交互、功能流程（反馈状态机）、边界（手机号 11 位、密码 6 位、年龄 1~120、日期区间）、约束（角色越权、账号工作状态）等；深入理解前后端分离架构（8080 devServer 代理 `/api` 到 9000）与接口约定（统一 `ResultVO{code,message,data}`）。
- **设计用例的优先级**：核心链路（登录→反馈→指派→实测→确认）为高优先级（冒烟集合），异常分支与管理类功能为中低优先级，按优先级筛选执行，节省时间。
- **从粗到细分析需求**：第一遍梳理角色-模块框架与状态迁移图；第二遍细化每个子测试点（等价类、边界值）；第三遍补充错误推测与场景用例（端到端链路、跨角色数据一致性）。
- **测试用例维护**：需求变更（如人员管理模块的请假表升级 `sql/hr_upgrade.sql`）时同步更新用例；评审阶段修整冗余或遗漏。
- **设计通用用例库**：将登录/注册、列表查询、增删改查、确认弹窗、分页等通用功能沉淀为通用用例，在本系统各模块间复用。

#### 3.2.2 测试用例作用

测试用例是软件测试的核心，如何以最少的人力、资源投入，在最短的时间内完成测试，发现软件系统的缺陷，保证软件的优良品质，则是测试工作追求的目标。

影响软件测试的因素很多，例如软件本身的复杂程度（本系统涉及 4 角色、12 模块、跨角色状态流转）、测试方法和技术的运用等等。因为有些因素是客观存在的，无法避免。有些因素则是波动的、不稳定的，例如开发队伍是流动的，有经验的走了，新人不断补充进来；一个具体的人工作也受情绪等影响。如何保障软件测试质量的稳定？有了测试用例，无论是谁来测试，参照测试用例实施，都能保障测试的质量，可以把人为因素的影响减少到最小。即便最初的测试用例考虑不周全，随着测试的进行和软件版本更新，也将日趋完善。

因此测试用例的设计和编制是软件测试活动中最重要的。测试用例是测试工作的指导，是软件测试必须遵守的准则，更是软件测试质量稳定的根本保障。

### 3.4 测试风险分析

**（一）设计方面**

- 风险：(1) 早期版本缺少详细设计说明书；解决方案：测试人员在开发阶段对相关设计及需求文档进行分析，对大体模块功能进行分类，分析业务逻辑（重点是反馈状态机与统计口径），在不清楚的地方及时与开发人员沟通。
- 风险：(2) 没有统一的界面设计规范；解决方案：与项目负责人确认测试标准（本系统采用统一"生态绿"设计系统与 GradeTag/StateTag 彩色标签，测试时以此为一致性基准）。

**（二）开发方面**

- 风险：(1) 所有模块开发没有统一设计，开发人员有自己的设计方式；解决方案：与项目负责人确认标准方式，与标准方式不一致的地方全部以 BUG 形式提交（如接口返回结构统一为 `ResultVO{code,message,data}`）。
- 风险：(2) 需求变更开发（如人员管理模块补充请假功能）；解决方案：建议将需求变更形成文档，对没有文档的需求变更，在测试过程中发现及时与开发负责人确认，并存档相关变更文档（对应 `sql/hr_upgrade.sql` 增量升级说明）。

**（三）测试本身**

- 风险：(1) 人力资源；解决方案：保证稳定的人员安排。
- 风险：(2) 硬件资源；解决方案：事先分析测试所需硬件资源（MySQL、JDK17、Chrome），及时申请，保证测试工作顺利进行。
- 风险：(3) 版本控制；解决方案：严格控制版本，BUG 以版本为单位进行提交。在测试过程中及 BUG 确认阶段禁止任何代码更新。
- 风险：(4) 测试时间不足；解决方案：动员测试人员完成测试任务，必要时给予相应物质奖励；通过 Selenium 自动化回归（见《自动化测试报告》）压缩回归周期。

测试风险是不可避免的、总是存在的，所以对测试风险的管理非常重要，必须尽力降低测试中所存在的风险，最大程度地保证质量和满足客户的需求。

## 4 系统非功能性测试

### 4.1 系统功能及测试点

**（一）性能测试**：应用在客户端性能的测试、应用在网络上性能的测试和应用在服务器端性能的测试。通常情况下，三方面有效、合理的结合，可以达到对系统性能全面的分析和瓶颈的预测。本系统测试点：列表/统计接口响应时间、页面首屏打开时间、中等并发下接口稳定性。

**（二）兼容性测试**：验证被测系统是否可以在各种可能的运行环境中正常工作。软件环境：现代浏览器（Chrome/Edge/Firefox）；操作系统：Windows 10/11、Ubuntu；硬件环境：1920×1080 / 1366×768 / 1280×800 分辨率及 1366 笔记本屏。

**（三）易用性测试**：用于核实用户与软件之间的交互，验收用户界面中的对象是否按照预期的方式运行，关注界面层和界面与功能的接口层。界面整体测试：评价用户界面的规范化、一致性和合理性；界面元素测试：关注对窗口、菜单、图标、文字、鼠标等界面中元素的测试。

**（四）安全测试**：软件安全性是与防止对程序及数据非授权的故意或意外访问能力有关的软件属性。针对本系统：密码存储与传输、登录鉴权与角色越权、敏感信息展示（手机号脱敏）、注入与 XSS 防护、异常信息泄露。

**（五）可靠性测试**：测试可靠性是指运行应用程序，以便在部署系统之前发现并移除失败。针对本系统：非法输入容错、状态机非法流转拦截、异常提示与数据一致性、错误操作可恢复性。
